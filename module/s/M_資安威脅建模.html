資安威脅建模

  • 為何 vibe coding 時代反而更該學：AI 預設只想「讓功能動」，不會主動幫你防壞人——它可能把密鑰寫死在前端、不檢查權限、不防注入攻擊。一旦你的小產品上線收了真實用戶資料，資安不是加分題，是會出大事的必答題（個資外洩、被盜用、法律責任）。威脅建模是「系統性地想『壞人會怎麼攻擊我』」的技術，補上 AI 最大的盲區。

核心

威脅建模（threat modeling）= 動工/上線前，有系統地問「這東西會怎麼被攻擊」。不是等出事才補，是事先想好。

STRIDE — 六類威脅的記憶法（逐項問「我這裡會不會」）： | 字母 | 威脅 | 白話 | | --- | --- | --- | | Spoofing | 假冒身分 | 有人冒充別的使用者登入 | | Tampering | 竄改資料 | 有人偷改金額、改別人的資料 | | Repudiation | 抵賴 | 做了壞事卻查不到是誰（沒留紀錄） | | Info disclosure | 資訊外洩 | 個資、密碼、密鑰被看到 | | Denial of service | 阻斷服務 | 灌爆流量讓服務癱瘓 | | Elevation of privilege | 越權 | 一般用戶拿到管理員權限 |

OWASP Top 10 — 最常見的網站漏洞清單（業界公認的「最該先防的十種」）。給非工程師記住最致命的幾個： - 注入攻擊（injection）：在輸入欄塞惡意指令操控資料庫（連回 邊界與例外案例設計：惡意輸入也是一種邊界）。 - 權限控制失效：沒檢查「這個人有沒有資格做這件事」，於是誰都能改誰的資料。 - 機敏資料外洩：密碼明文存、密鑰寫在前端、走未加密連線。 - 設定不當：用預設密碼、把除錯模式開在正式環境。

vibe coding 的三條保命底線（AI 不提你也要主動要求）： 1. 密鑰/密碼絕不寫死在前端或 commit 進 Git——用環境變數。 2. 任何「改/看資料」的動作都要先檢查身分與權限。 3. 所有使用者輸入都當成「可能有惡意」來處理——驗證、過濾、別直接信任。

vibe coding 接法：上線前拿 STRIDE 逐項問一遍你的產品，把「安全需求」明確寫進給 AI 的規格（連回 非功能需求），並特別要求 AI 檢查 OWASP 常見漏洞。收真實用戶資料前，這關不能跳。

💬 互動

  • 一起想一題：一個「線上問卷收集個資」的小工具，用 STRIDE 想，最該擔心哪 3 種威脅？各舉一個防法。

  • 反思：「我 vibe code 的東西如果上線收了真人資料——AI 有沒有幫我防壞人？還是我從沒問過這件事？」

  • 小作業：拿你一個（打算）上線的產品，用 STRIDE 跑一遍列出威脅，對照三條保命底線檢查 AI 的版本有沒有踩雷。
