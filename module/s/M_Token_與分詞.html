M Token 與分詞

  • 一句話：LLM 不是一個字一個字讀，而是把文字切成 token（介於字與詞之間的碎片）。模型的「視野」「記憶」「帳單」全部以 token 計。

核心

什麼是 token：一段文字被切成小塊。英文約「4 個字元 ≈ 1 token」「一個常見單字 ≈ 1 token」；中文常常一字一 token 甚至更碎。"unbelievable" 可能切成 un + believ + able 三塊。

三個必須記住的後果：

  1. Context window 是用 token 算的：模型一次能看的上限（例如 20 萬 token）是 token 數，不是字數。塞進去的資料、對話歷史、你的指令，全部一起佔額度——爆了就從最舊的開始被擠掉（截斷）。這是 context engineering 的核心約束（連回 M Harness Engineering 與資訊熵）。
  2. 成本與速度按 token 計：API 收費、回應快慢都跟 token 數成正比。「把 prompt 寫精簡」不只是文風問題，是省錢省 context。
  3. 分詞會造成怪 bug：模型「看不清」一個被切碎的詞——所以它常算錯「strawberry 有幾個 r」、處理罕見專有名詞或數字會出錯。那不是它笨，是它根本沒看到完整的字。

連回 entropy／生成：模型每一步預測的是「下一個 token」的機率分布（連回 M Autoregressive 生成與取樣），不是下一個「字」。理解 token 才理解它真正在預測什麼。

💬 互動

  • 配對：估一估——你常用的一份 prompt 大概幾百 token？一份 10 頁 PDF 塞得進 20 萬 token 的 context 嗎？（粗估：1 頁約 500 字 ≈ 700+ token）

  • 反思：「我之前以為 context 不夠是『話太多』，現在我知道那是 token 預算用完了。」

  • 小作業：把一段你常丟給 AI 的長 prompt，試著砍掉一半 token 又不掉資訊，記錄前後差別。
