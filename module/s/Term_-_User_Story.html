User Story｜使用者故事

User Story

One requirement written as "as a ⟨kind of user⟩ I want ⟨to do something⟩ so that ⟨I get some result⟩".

把一條需求寫成「身為〈某種使用者〉，我想要〈做某件事〉，以便〈得到某個結果〉」的一句話。

What this term means｜這個詞在說什麼

The sentence pattern exists to force you to state the reason. The third clause is the actual requirement; the first two are packaging. Without it, an engineer cannot judge whether there is a better way to get the same result.

A user story has to be verifiable, so it usually travels with a set of acceptance criteria.

這個句型的用處是逼你寫出理由。第三段（以便…）才是真正的需求；前兩段只是包裝。沒有第三段的 user story，工程師無法判斷有沒有更好的做法。

一條 user story 要能被驗收，所以它通常配一組驗收條件。

Common misconceptions｜常見誤解

  • Dropping a feature name into the pattern: "as a user I want a search box" — no reason, therefore no requirement.

  • Packing three things into one story. If it will not split, you have not thought it through yet.

  • 把功能名稱套上句型就交差：「身為使用者，我想要一個搜尋框」——這裡沒有理由，也就沒有需求。

  • 一條 story 塞三件事。拆不開通常代表你還沒想清楚。
