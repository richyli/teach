Prompt Structure and Sub-agents

This unit covers why the same instruction produces different results for different people, how a working brief differs from a prompt, and what a second agent with its own clean context is for.

🎯 Learning objectives

# What you will be able to do The real problem it lets you answer
1 Explain why an identical instruction produces different output for two people, in terms of context rather than luck "It worked for her." Same tool, same sentence, different result — and the variable is almost never the model.
2 Turn a three-part instruction into a working brief by adding constraints and a statement of what done looks like Your instruction was clear and the output was still wrong. Clear is not the same as complete: you never said when to stop.
3 Decide when a task needs a second agent with its own context, and when a second agent only fragments the work Everyone is impressed by ten agents running at once. Which of your tasks actually gets better, and which just gets harder to check?
4 Judge whether a verification step is real or ceremonial, using whether the verifier could see the reasoning it is checking An agent that reviews its own work in its own context is grading its own exam and will pass.

🤖 Pre-class AI workout

Use an AI as your study partner before class. Paste the prompt below.

Here is an instruction I gave an AI assistant last week: "Summarise this report for my team." It produced something I could not use. Do not rewrite it for me yet. Instead, list every decision the assistant had to make that my instruction did not decide for it — how long, for whom, what to leave out, what counts as important, what tone, what to do with things it was unsure about. Then tell me which one of those decisions, if I had made it explicitly, would have changed the output the most. Answer in a list, no preamble, and do not congratulate me on asking a good question.

Then ask it this one question:

Which of those decisions would you still get wrong even if I specified it, and why?

Bring the single decision it named as most consequential. Most of the room will bring the same one, and that tells you which part of an instruction people habitually leave out.

The same instruction lands differently because the context differs

Two people type the same sentence and get different output. The sentence is identical, so the difference is everything around it: which files were open, what was said earlier in that session, which folder it was started in, what it had already been told to avoid.

This is the practical meaning of "context". Not a setting — everything the model can see at the moment you press enter. The instruction is the smallest part of it.

Context is a budget, not a bucket

Everything competing for attention in one session dilutes everything else. A session where you have been chatting for an hour about three different tasks is a worse place to give a precise instruction than a fresh one, because your careful sentence is now sharing space with fifty exchanges about something else.

The practical rule is unglamorous: one task, one session. Start a new one when the subject changes, rather than accumulating a session that "knows everything" — that session knows everything equally, which is the problem.

Attention is what you are actually rationing. Anything in the context that is not helping this task is competing with it.

A brief is a three-part instruction plus the two things people leave out

Context, task and output format get you a usable result. Two more turn it into something you can hand over and check.

Constraints — what it must not do. Do not invent numbers that are not in the source. Do not change the quotes. Do not touch any file outside this folder. Constraints are where you write down the failures you have already seen.

What done looks like — the test the output has to pass before you would accept it. Every claim traceable to a line in the transcript. Under 200 words. A named alternative for every recommendation.

Unspecified is not neutral

Whatever you leave out gets filled in with the most ordinary plausible default. Nobody chose that default and nobody is accountable for it, but it is now in your document.

Tekton's advice after winning the Opus 4.8 Build Day hackathon was to map the entire project before building any of it — they wrote a fifty-ticket specification before letting the model start (Claude Build Day Hackathon). Another winning team spent two full days on design and specification with no code written, and reported that the slow start made everything afterwards faster (Opus 4.7 Claude Code Hackathon).

The vocabulary for "what done looks like" is acceptance criteria, and W11 spends a whole session on writing them. You are meeting the idea now because it is already deciding the quality of your output this week.

A sub-agent is a second worker with its own clean context

Instead of one agent carrying everything, you hand a defined job to a second one that starts fresh, does that job, and reports back. The main session stays clear, and the second one is not distracted by history that has nothing to do with its task.

Three shapes cover most real uses. Verification: one agent produces, a second one checks, and the checker never sees the reasoning that produced the work. Breadth: several agents work different parts at once, which is how one hackathon team ran five or six in parallel to debug a circuit-board tool. Separation: distinct areas of a build get their own sessions, as with the team that ran four — voice, content, the 3D layer, and the core application (Opus 4.7 Claude Code Hackathon).

Isolation is the whole point of a verifier

Tekton's verification sub-agents scored the reconstruction in isolated contexts, and a self-correction loop kept going until twenty tests passed (Claude Build Day Hackathon). The isolation is not a technical detail. An agent asked to check work it can see itself producing has every reason the original had to believe it was right, and it will tell you so.

Ask one question of any verification step, human or machine: could the checker see the reasoning? If yes, you have a second opinion from the same opinion.

For students · The same test applies to your own drafts

This is why you cannot proofread your own writing an hour after finishing it, and why the W8 pitch is judged by people who did not watch you build it. Isolation is not distrust, it is the only condition under which a check produces new information.

More agents is not more capability

Each additional agent adds something you have to read, reconcile, and eventually be responsible for. Sub-agents earn their place when the sub-task is genuinely separable and its output can be judged on its own. They cost you when the task needs shared memory, when the pieces have to agree with each other, or when nobody is going to read the extra output anyway.

⚠️ Common misconceptions

What students assume Why it is wrong What to do instead
"It worked for him because he has the paid version" The dominant variable is context — which files, which session, what was said before Compare the two sessions, not the two subscriptions
"A long session that knows everything is better" Everything in the context competes for attention with your current task One task, one session
"My instruction was clear, so it was complete" Clear says what to do. Complete also says what not to do and when to stop Add constraints and what done looks like
"Asking it to double-check its own answer is verification" Same context, same reasoning, same conclusion Give the check to something that cannot see the reasoning
"Running five agents is more powerful" Five outputs is five things to reconcile, and someone still has to read them Split only what can be judged separately
"Specifying everything up front is slow" Two of the hackathon winners started with days of specification and said it made everything faster Spend the time before the first run, not after the third

In short

  • The variable behind "it worked for her" is context, and context is a budget you spend rather than a bucket you fill.
  • A brief adds two things to an instruction: what it must not do, and what done looks like. Both are written from failures you have already seen.
  • A sub-agent is worth spawning when the sub-task can be judged on its own, and a verifier is worth having only if it cannot see the reasoning it is checking.
  • Anything you leave unspecified still gets decided. Just not by you.

💬 Discussion and reflection

Pair review

The situation. Your group report is due on Monday. One member ran the whole draft through an AI in a single session that has been open since Tuesday and also contains the group's argument about who does the slides, a half-finished budget, and two abandoned outlines. The draft that came back is fluent, confidently states a statistic nobody can find in the sources, and has quietly dropped the one section your lecturer asked for.

  1. Name which of the two rules explains each of the three problems — the session that knows everything, or the instruction that never said what done looks like
  2. Write the two lines you would add to the instruction: one constraint, one statement of what done looks like
  3. Decide who or what should check the rewritten draft, and say why that checker can see something the author cannot

情境：小組報告星期一要交。有位組員把整份草稿丟進一個從星期二就開著的 session，那個 session 裡還有你們吵誰做投影片、一份沒填完的預算，和兩份放棄掉的大綱。回來的草稿很順，很有自信地寫了一個沒人找得到出處的數字，還悄悄漏掉老師指定要有的那一節。

  1. 三個問題各由哪一條規則解釋——是那個什麼都知道的 session，還是那條沒說「怎樣算完成」的指令
  2. 寫出你要補上的兩行：一行限制、一行完成判準
  3. 決定改好的草稿該由誰或由什麼來檢查，並說出那個檢查者能看到作者看不到的什麼

Individual reflection

Write one sentence to keep: "The decision I habitually leave to the AI without noticing is __, and next time I will state it as ____."

✍️ Take-home task

Take the instruction you wrote in the first session of this week and add the two missing pieces — one constraint and one statement of what done looks like. Run it again on the same material and keep both outputs. One paragraph on what changed.
