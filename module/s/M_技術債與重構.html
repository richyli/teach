技術債與重構

  • 為何 vibe coding 時代反而更該學：AI 能極快堆出「能動」的程式，但快速堆疊最容易累積技術債——一坨會動、但越來越亂、越來越沒人（包括 AI 自己）改得動的程式。很多人 vibe code 到一半「卡死」，不是做不出新功能，是舊的爛攤子讓任何改動都會弄壞別的地方。看得懂技術債、知道何時該重構，是讓專案能「持續長大」而非「中途崩盤」的關鍵。

核心

技術債（technical debt）= 為了快，先用爛做法，欠下「以後要還」的整理成本。像借錢：短期跑得快，但利息會滾——債越多，每加一個新功能就越慢、越容易出包。

vibe coding 為何特別容易欠債： - AI 為「讓它先動」常產出重複、雜亂、硬寫死的程式。 - 你看不太懂，於是不敢動、只敢一直疊上去 → 債滾債。 - 徵兆：改一個小地方就壞三個別的；同樣的邏輯散落好幾處；AI 自己也開始改不對了。

重構（refactoring）= 不改變外部行為，只把內部整乾淨。功能一樣，但程式更清楚、更好改。關鍵：重構不是加功能，是還債。

安全重構的兩個前提（缺一不可）： 1. 先有測試：重構前要有測試保證「整理完行為沒變」（連回 驗收測試與 TDD-BDD）。沒測試的重構 = 拆牆不知道哪面是承重牆。 2. 先 commit：整理前存安全點，弄壞了退得回（連回 版本控制與 Git 心智模型）。

何時該停下來還債（給非工程師的判準）： - 連續好幾次「加小功能卻花超久 / 一直弄壞別處」→ 該重構了。 - AI 開始反覆改不對同一塊 → 那塊太亂，先請它整理再說。 - 定期還小債 > 累成大債一次爆。

vibe coding 接法：把「請 AI 重構這段、不要改行為、讓它更清楚好改」當成定期動作，重構前先確認有測試＋已 commit。別一路狂疊到崩盤——會動 ≠ 養得起（連回 非功能需求 的可維護性）。

💬 互動

  • 一起想一題：一個 vibe code 的專案，前兩週超快、第四週幾乎加不動新功能，發生了什麼？該怎麼辦？

  • 反思：「我是不是只要『能動』就一直往上疊？有沒有定期請 AI 幫我把程式整乾淨？」

  • 小作業：挑一個你疊得有點亂的 vibe coding 專案，確認有測試與 commit 後，請 AI 重構一段並驗證行為沒變，記錄改動前後好不好讀。
