驗收測試與 TDD/BDD

  • 為何 vibe coding 時代反而更該學：當程式是 AI 寫的、你看不太懂時，你唯一可靠的把關方式，是「測試會不會過」而不是「我讀懂了程式」。測試是你對 AI 產出的自動化信任機制。會定義「怎樣算對」並讓它自動驗，比會讀 code 更重要。

核心

測試的核心觀念：寫一段「會自動檢查程式對不對」的東西。給定輸入，預期輸出是什麼，符合就過、不符就紅燈。人會偷懶漏驗，測試不會。

TDD（測試驅動開發）= 先寫測試，再寫程式： 1. 先寫一個「現在一定失敗」的測試（描述你要的行為）。 2. 寫剛好讓它通過的程式。 3. 整理程式，保持測試綠燈。 - vibe coding 版：先把「驗收條件」變成測試，再叫 AI 去寫到測試通過。測試成了給 AI 的精確目標與自動驗收（連回 User Story 與驗收條件）。

BDD（行為驅動開發）= 用人話描述行為當測試：直接把 Gherkin 的 Given-When-Then 變成可執行的測試（連回 規格書與 Gherkin 行為規格）。好處是非工程師也讀得懂測試在驗什麼——需求、規格、測試是同一份。

三層測試的最小認識： - 單元測試：驗一個小零件對不對（這個函式算錢算對嗎）。 - 整合測試：驗幾個零件接起來對不對（下單後庫存有沒有減）。 - 驗收測試：驗「使用者要的那件事」整條走得通（user story 達成了嗎）。

vibe coding 接法：把驗收條件 → 測試 → 叫 AI 寫到綠燈 → 改動後重跑全部測試（回歸測試，防止改 A 弄壞 B）。測試是你在看不懂 code 的情況下，仍能安全迭代的安全網——這正是 vibe coding 規模化的關鍵。

💬 互動

  • 一起想一題：AI 幫你改了一個功能，怎麼確定它沒順手弄壞別的地方？（回歸測試）為什麼「我手動點一點看起來沒事」靠不住？

  • 反思：「我驗 AI 的產出，是靠『讀懂程式』還是靠『跑得過測試』？前者我做不到，後者我做得到。」

  • 小作業：把你一個功能的 3 條驗收條件寫成 3 個測試（可請 AI 協助），叫 AI 寫程式到全綠，再故意改壞一處看測試會不會抓到。
