M User Story 與驗收條件

  • 為何 vibe coding 時代反而更該學：你能叫 AI 幾秒生出一個功能，但如果你講不清「為誰、要什麼、怎樣算對」，它只會又快又精準地做錯東西。User story 把需求壓成一句「誰、想做什麼、為了什麼」，驗收條件則是「怎樣算做完」——這正是給 AI 的高品質指令（連回 M 訊號與雜訊：精準需求 = 高訊噪比的 context）。

核心

User Story 標準句型：

As a（什麼角色）, I want（做什麼）, so that（得到什麼價值）。

例：「身為通勤族，我想離線下載文章，以便在沒網路的捷運上閱讀。」三段缺一不可——少了角色會做錯對象，少了 so that 會做出「能用但沒人要」的功能。

INVEST 好故事六標準：Independent（獨立）、Negotiable（可協商）、Valuable（有價值）、Estimable（可估量）、Small（夠小）、Testable（可驗收）。一句故事大到塞不下一輪迭代，就該拆。

驗收條件（Acceptance Criteria）= 怎樣算做完：把「我想離線閱讀」變成可勾的清單—— - 已下載的文章在飛航模式下能開 - 下載中斷後重連能續傳 - 超過 50 篇時提示清理

vibe coding 接法：把 user story + 驗收條件直接當成給 AI 的規格，再把每條驗收條件當成驗收測試（連回 M 驗收測試與 TDD-BDD）。AI 做完後逐條對——這就是你的品管。沒有驗收條件，「做完了」只是 AI 的一面之詞。

💬 互動

  • 配對：各拿一個想做的小功能，互相用標準句型寫成 user story，並逼對方補出 3 條驗收條件。

  • 反思：「我之前叫 AI 做東西，是不是只說了『要什麼』，沒說『怎樣算對』？難怪它做的跟我想的不一樣。」

  • 小作業：把你最想 vibe code 的一個產品，拆成 5 個 user story，每個配 2–3 條可勾的驗收條件。
