PRD 撰寫與壓力測試

  • 理論：Boundary Object Theory（主）——PRD 把跨活動系統的共同規則編碼、凍結一次 sensemaking 結果；輔以 Activity Theory（rules）、Sensemaking。與 W7 的 MRD 構成同學期兩個對照邊界物件。
  • Flip Exercise｜PRD Stress Test：A 組寫 PRD → B 組把它丟給 AI agent、直接出貨 agent 產出的東西 → C 組審查產出、揪出每個規格漏洞與默會假設。
  • 小作業：繳交修補後 PRD + 漏洞清單。

真實 PRD 範本：Tekton / Yingzao（Build Day 冠軍）

全文教材：Tekton PRD (Build Day 冠軍範本)（已下載原檔）。來源 Claude Build Day Hackathon。一份 ~6,500 字、13 章節的真實得獎 PRD，課堂直接拿它當「一份好 PRD 長什麼樣」的範本，比抽象講章節有力。

  • 13 章節結構：①One-Line Punch ②Product Summary ③Why This Matters ④Founder Story ⑤Subject Buildings ⑥UX（六層，明言 Not a Chatbot）⑦Reconstruction Pipeline（5 個 agent 子節）⑧Build-Day Orchestration（時程/事前 vs 當日分工）⑨Data Sources & Rights ⑩MVP Scope ⑪Tech Stack ⑫Definition of Done（9 項）⑬Submission Checklist。
  • 三個教學點：
  • One-Line Punch = reframing：「把『對』做得比『像』便宜」（right cheaper than looks-like）——PRD 第一句就是問題重新定義。
  • 明確「不做清單」（§10 禁止聊天框 / 帳戶 / CMS / 超過三棟）——範例級的 anti-scope-creep，接 範疇管理與優先級。
  • 驗收前置而非當日選擇：顏色作為 design token 預先凍結、部署為 frozen verified artifacts（無 runtime LLM）——對應 §12 Definition of Done。
  • 注意：50 張工單在 Notion 看板（不在 PRD 內），PRD 本身不放個別 ticket——示範「PRD（規格）vs 工單（執行）分屬不同邊界物件」。

💬 討論／分享／反思

  • 配對互評：兩人一組，互換各自寫的 PRD（或剛修補完的版本），扮演「惡意 AI agent」逐條挑刺——找出對方規格裡「字面照做就會出錯」的句子、沒寫的 edge case、藏起來的默會假設。各自至少幫對方標出兩個漏洞。
  • 一起收斂一題：老師收集大家挑到的漏洞，丟出一題讓全班表態——「PRD 要寫到多細才夠？當 AI 會用『看似合理但錯誤』的預設填空，把邊界畫在哪裡才划算？」對照 Tekton 範本的「不做清單」與 Definition of Done，看好的 PRD 是靠窮舉細節還是靠凍結驗收標準。
  • 寫下個人反思：每人寫一句帶走——「我的 PRD 最容易被 AI 誤讀的一個地方是 ，下次我會用 （acceptance criteria／不做清單／預先凍結 token）把它釘死。」
