Claude Code 指南 6｜skill：把重複的工作固化

在本單元中，會介紹什麼樣的工作值得做成 skill、一個 skill 的檔案長什麼樣、怎麼把你的三段式指令存成一個可以喊名字叫用的東西，以及為什麼別人拿去跑才算真的做好了。

skill 不是新東西，是你那串指令被存起來

你每週五都在打同一段話：「把這週發的稿整理成主管週報，每篇三行，附連結。」打第五次的時候你就該把它存起來。

存起來、給它一個名字，就叫 skill。下次打 /週報彙整 就跑。

對不同背景的人有不同的說法：對用過 Office 的人，它像巨集；對工程師，它像函式；對你，它就是一份 SOP。

三條判準，缺一條就先別做

判準 問自己
頻率高 這件事我每週、每天都在做嗎？一次性的事固化了也用不到
步驟固定 流程大致一樣嗎？還是每次都長得不同
輸入輸出講得清楚 我說得出丟什麼進去、要吐什麼出來嗎

反例校正：「幫我想一個 idea」不適合，步驟不固定、輸出也說不清。「把這週五篇稿子彙整成一頁主管週報，每篇三行、附連結」非常適合，三條都中。

一個 skill 就是一個資料夾加一個檔案

~/.claude/skills/週報彙整/
└── SKILL.md

資料夾的名字就是你要打的指令名稱。SKILL.md 的上半部是設定，下半部是給它看的步驟，沒有程式碼。

放的位置決定誰用得到：

放哪 路徑 誰用得到
你自己 ~/.claude/skills/<名稱>/SKILL.md 你這台機器上的所有專案
這個專案 專案資料夾/.claude/skills/<名稱>/SKILL.md 打開這個資料夾的所有人，可以給團隊共用

判斷法：指令裡寫死了某個專案路徑，放專案；是一個到哪裡都能用的工具，放你自己那一層。

一份可以直接改用的 skill

把下面這段存成 ~/.claude/skills/週報彙整/SKILL.md：

---
description: 把本週稿件清單整理成一頁主管週報。使用者說要做週報、
  要彙整本週稿件、或提到週五週報時使用。
---

# 週報彙整

## 你的角色
你是我的編務助理。我每週五會給你這週發布的稿件清單。

## 步驟
1. 逐篇抓出一句話重點，不超過三十字
2. 標出哪幾篇的數據表現最好，並說明是哪一個指標
3. 彙整成一頁，每篇三行以內，附原文連結
4. 最後給三句下週選題建議，每句要指得回上面某一篇

## 輸出格式
- Markdown，控制在一頁
- 主管掃一眼就懂，不要有我需要再問一次的地方
- 找不到連結的篇目標〔缺連結〕，不要自己編

上半部那幾行是設定，兩個 --- 中間的部分。裡面最重要的是 description：它靠這一句決定要不要自己叫出這個 skill。寫得模糊，它就不會在該用的時候用。把使用者實際會說出口的說法寫進去，效果最好。

下半部就是你原本要打的那串話，只是拆成了角色、步驟、格式。你有沒有發現，這三塊就是指南 3 的三段式。

另外兩個現成的場景

選題評估 查證清單
角色 選題會的幕僚 事實查核員
步驟 對每個提案打三個分（時效、獨家性、可執行性），各附一句理由，最後給排序 把稿子裡每個可查證的事實列出來，標出哪些有附來源、哪些沒有
格式 表格，分數加一句話 清單，沒來源的排最前面

三個場景的共同點是：輸入是一份現成的東西，輸出是一張別人看得懂的表。這類工作最適合第一個拿來固化。

兩種叫用方式，跟一個你會想關掉的行為

打 /週報彙整 是你主動叫它。另一種是它自己判斷相關就載入，靠的是那句 description。

有些 skill 你不希望它自己決定要不要跑，例如會寄信、會發布、會覆蓋檔案的。在設定區加一行：

disable-model-invocation: true

加了之後，只有你打 /名稱 才會跑。任何有對外副作用的動作都該加這一行。

讓 skill 吃參數

同一個 skill 想套用在不同對象上，用 $ARGUMENTS：

---
description: 把一份素材改寫成指定平台的版本
---

把我給你的素材改寫成 $ARGUMENTS 版本，符合該平台的語氣與長度限制。
不確定的事實一律標〔待確認〕，不要自己補。

之後打 /改寫 LINE 群組通知，$ARGUMENTS 就會變成「LINE 群組通知」。

這一招讓「一稿多版」從四個 skill 變成一個。

需要算數或批次處理的時候，讓它寫腳本

文字、判斷、寫作這類事，直接寫在 SKILL.md 裡讓它自己做。碰到精確計算、一次處理上百個檔、呼叫別的系統，就該讓它寫一支腳本，SKILL.md 只負責叫那支腳本跑。

理由有三個：純計算交給程式比較不會錯，跑起來快得多，而且你不開 Claude Code 也能直接跑那支腳本。

你不需要會寫 Python。描述你要什麼，它會寫、會除錯、會放好，再幫你把 SKILL.md 寫成叫它跑的樣子。你負責提需求、看結果、講哪裡錯了。

skill 是調出來的，不是寫出來的

第一版一定給你很普通的東西。真正有用的版本是這樣長出來的：

  1. 你叫它跑
  2. 它做出九成對的東西
  3. 你看出那一成不對，講「應該是 X 不是 Y」
  4. 它修正當下的結果
  5. 你接著說：把這個規則寫進這個 skill
  6. 下次跑就對了

第五步是最多人漏掉的。光糾正一次，下次還會犯。

有一個內部案例可以當尺度感：某個要模仿特定主管文風的 skill，改了好幾百次系統提示才真的像本人。用第三版的表現去判斷一個 skill 值不值得留，不要用第一版。寫完一次就丟在那裡的 skill，只是一段多繞了幾步的提示。

別人拿去跑才算做好

一個只有作者在旁邊才跑得動的 skill，還停在提示階段。

檢驗方法很直接：把你的 skill 交給同事，讓他拿一份你沒看過的材料去跑。看他必須回頭問你什麼問題，那個問題就是你留在腦袋裡、沒寫進 skill 的部分。把他問的問題補進去，就是下一版。

你寫進去的不只是步驟，還有判斷

上面那個週報 skill 裡，有人決定了：重點寫一句不是三句、每篇三行不是五行、下週建議要指得回某一篇。這些都是判斷，不是步驟。

同事拿去用，等於在沒有討論過的情況下接受了這些判斷。這解釋了兩件事：一個團隊共用 skill 之後產出會開始長得像同一個人；一個沒被檢查過的共用 skill，會把一個人的盲點複製到所有人的產出上。

這對主管的意義是：哪些判斷可以寫進共用 skill、哪些必須留給個人，是編輯政策問題，不是技術問題。

有人的一天長什麼樣

給一個累積之後的尺度感。有人每天早上跑一個指令，接下來自動完成：讀完資料夾裡新進的論文 PDF 並寫成筆記、掃各國媒體整理成一份分類新聞簡報、抓穿戴裝置資料寫成睡眠分析、把任務清單依期限重排並同步到看板。整個過程沒有打字，就一個指令，沖咖啡的時間跑完。

那不是一次做出來的，是一個一個 skill 累積兩年的結果。你這週要做的只是第一個。

帶回你的編輯室

  • 你單位哪些固定產出（週業務簡報、月競品動態、日客服摘要）可以先變成 skill？
  • 這些報告現在誰在做？時間還給他之後，他該做什麼更值錢的事？
  • 資深同事的判斷力要怎麼合法地蒸餾成 skill？他願意嗎？該怎麼算他的貢獻？
  • skill 就是一個文字檔，同事複製走明天就能在別家用。這是你要防的重點嗎？還是防不住之後，你該重新盤點的是別的東西？

檢查清單

  • [ ] 你挑的那件事三條判準都中
  • [ ] SKILL.md 裡有角色、步驟、格式三塊
  • [ ] description 寫了你自己會說出口的觸發說法
  • [ ] 有副作用的 skill 加了 disable-model-invocation: true
  • [ ] 你跑過至少兩次，第二版比第一版好
  • [ ] 你交給另一個人跑過，並把他問的問題補進去了
