Harness Engineering 與資訊熵

  • 誰該聽：要跟工程師談 agent 系統、或自己用 Claude Code／agent 做事的人。

Harness 是什麼？它的工作就是「餵資訊」

LLM 的本質：給定目前的上下文，輸出「下一個 token 的機率分布」。這個分布有它的 entropy——分布越平、模型越「不知道該說什麼」，就越容易亂猜（幻覺）。

Harness（鷹架）就是包在 LLM 外面的那層工程：決定餵什麼進去、模型能用什麼工具、記得什麼、輸出怎麼被檢查。典型組件：

Harness 組件 它在做的事（用 entropy 語言講）
System prompt / 指令 把任務的可能解釋從一大堆砍到一小撮
Context（餵的資料） 直接灌進「消除不確定性」的 bits
工具（檢索、執行、查 API） 讓模型主動去「問是非題」，自己砍 entropy
記憶 / 狀態 不讓先前已消除的不確定性又冒回來
輸出結構（schema、驗證） 限縮輸出空間，等於先砍掉一堆不合法分支

一句話：Harness engineering = 不確定性工程。 你不是在「教模型更聰明」，你是在「把它下一步的 entropy 壓低到能可靠行動」。

用 entropy 解釋三個 harness 現象

回憶上一模組：entropy 高 = 分布均勻 = 最不可預測；餵對的資訊 = 砍掉不確定性 = entropy 下降。下面三個工程現象，全是同一件事。

現象一：context 不足 → 它就亂補（幻覺）

你問「我們上週那個案子結論是什麼？」模型沒有那份檔案，對「結論是什麼」的分布幾乎是均勻的——一堆似是而非的答案機率差不多。高 entropy 的分布，sample 出來就是亂編。

  • harness 解法：檢索把那份檔案塞進 context → 分布從均勻塌縮到一個尖峰 → entropy 趨近 0 → 它只能照著講。
  • 這就是 RAG / 工具呼叫的本質：不是讓模型「更聰明」，是幫它把 entropy 砍下來。

現象二：為什麼「給足 context」這麼重要

把 harness 想成一連串「砍一半」的是非題（呼應猜數字遊戲）。每一塊到位的 context、每一次成功的工具呼叫，都是一個高資訊量的問題——一刀砍掉一半的可能世界。

  • context 給得精準 → 每塊都砍掉一半 → 幾塊就收斂。
  • context 給得雜、矛盾 → 等於問了一堆「是 1 嗎？」的爛問題，砍不動、還可能把 entropy 加回去（模型在互相矛盾的資料間更迷惘）。

設計準則：不是「塞越多越好」，是「每一塊 context 的邊際資訊量越高越好」。塞滿無關資料 = 稀釋 + 加噪 = entropy 不降反升。

現象三：工具與結構化輸出 = 讓模型自己砍 entropy

  • 給模型一個搜尋工具，等於授權它去「主動問是非題」——它每查一次，就為自己消一份不確定性。好的 agent harness 就是把這個「自己砍 entropy」的迴圈設計好。
  • 強制結構化輸出（JSON schema），等於事先把輸出空間裡「不合法的分支」全部歸零，剩下的機率重新分配——直接降低出格亂答的 entropy。

主管 / 使用者視角：該問什麼、該怎麼餵

把 entropy 當共同語言，跟工程師（或對自己）問對問題：

該問工程師的三題（entropy 版） 1. 「這個 agent 下一步靠什麼資訊收斂？context window 多大、檢索餵不餵得進來？」（→ 它有沒有足夠 bits 砍 entropy） 2. 「它亂答的時候，通常是哪一類不確定性沒被消掉——缺資料、缺工具、還是指令太鬆？」（→ 定位 entropy 來源） 3. 「我們怎麼驗證它不是在高 entropy 下硬猜？有沒有讓它『不確定就說不知道 / 去查』？」（→ 不確定性的安全閥）

自己用 agent 的三個動作 1. 先餵高資訊量的 context：把最能「砍一半」的關鍵檔案、規格、限制先給足，別丟一堆無關背景稀釋它。 2. 給它砍 entropy 的工具：能查的就讓它查，不要逼它用記憶硬掰。 3. 可疑就追問來源：輸出很「滑順但空泛」常是高 entropy 硬 sample 的徵兆——要它列依據。

界線提醒（呼應 資訊理論與不確定性）：「給足 context」和「把商業機密貼給外部 AI」是兩回事。砍 entropy 要用對的、可外洩的資訊；機密走內部部署或去識別化。

這一堂收束成一句話：Agent 會不會做事，取決於你有沒有把它下一步的 entropy 餵到夠低。Harness engineering 就是不確定性工程——每一塊 context、每一個工具，都是一刀砍向不確定性。

💬 討論／分享／反思

  • 配對分享：各舉一次「agent／AI 因 context 不足而亂補」的親身經驗，互相用 entropy 語言重講一遍——「當時它的分布為什麼是均勻的？補哪一塊 context 能把 entropy 砍下來？」
  • 一起想一題：有人說「context 塞越多越準」。用這一堂反駁：什麼情況下塞更多 context 反而升高 entropy、讓 agent 更糟？（答：無關／矛盾資料加噪、稀釋邊際資訊量）

  • 反思：「我以前以為把 agent 做好 = 找更強的模型；現在我會先問——我有沒有幫它把下一步的不確定性砍到夠低？」

  • 小作業：挑一個你想交給 agent 的任務，畫出它的「entropy 砍除路徑」：列出 (1) 一開始模型對哪些事是高度不確定的；(2) 哪三塊 context／哪些工具最能各砍一半；(3) 哪裡需要一個「不確定就停下來問 / 查」的安全閥。
