API 設計與契約

  • 為何 vibe coding 時代反而更該學：你做的東西幾乎都要「串別人的服務」（金流、地圖、AI 模型、登入），或讓「前端串自己的後端」。這些接點就是 API。AI 能幫你呼叫 API，但如果你不懂「契約」——誰要傳什麼、會回什麼、出錯回什麼——它接錯了你也看不出來。API 契約是讓兩邊（前後端、你和第三方、你和 AI）先講好規格再各做各的的技術。

核心

API = 一個服務對外開放的「點餐窗口」：你不必知道廚房怎麼運作，只要照菜單點、它就照規格回。契約（contract）= 那張菜單寫死的規格：有哪些端點、每個要傳什麼、會回什麼。

最該認得的觀念（以常見的 REST 為例）： - 端點與動作：用網址 + HTTP 動詞表達「對什麼做什麼」——GET /orders（查訂單）、POST /orders（建訂單）、DELETE /orders/123（刪第 123 筆）。 - 請求與回應：傳進去什麼（參數、JSON body）、回來什麼（通常是 JSON，結構要固定，連回 ERD 資料模型 的資料結構）。 - 狀態碼：200 成功、400 你傳錯、401 沒權限、404 找不到、500 它壞了——出錯的回應跟成功的一樣重要（連回 邊界與例外案例設計）。 - OpenAPI / Swagger：把上述契約寫成一份機器可讀的規格檔，前後端照它各做各的、還能自動生文件與測試。

契約優先（contract-first）的威力：先把 API 契約談定，前端、後端、AI 就能並行開發，各自照契約做，最後一接就通。先定契約 = 先消除「我以為你會傳這個」的災難。

vibe coding 接法：(1) 串第三方前，先讀它的 API 文件，搞清楚契約（要金鑰嗎？回什麼格式？錯誤碼？）再叫 AI 寫串接；(2) 自己做前後端時，先請 AI 產一份 OpenAPI 契約並和你對齊，再讓它分別實作兩端。契約是兩邊之間的單一事實來源（連回 規格書與 Gherkin 行為規格）。

💬 互動

  • 一起想一題：你要串一個「寄 email」的第三方服務，動工前該先搞清楚契約的哪 4 件事？（要金鑰嗎？傳什麼欄位？成功/失敗怎麼回？有沒有次數限制？）

  • 反思：「我叫 AI 串外部服務時，是不是沒先讀懂它的契約？接錯了、或它改了規格，我根本不會發現。」

  • 小作業：挑一個你想串的服務，列出它契約的關鍵欄位與錯誤碼；或請 AI 為你的小產品產一份 OpenAPI 契約，檢查端點與回應結構合不合理。
