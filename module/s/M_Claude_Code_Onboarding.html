Claude Code Onboarding

This unit covers what makes Claude Code an agent rather than a smarter chat box, how to get it running on your own machine, and how to write one instruction it can actually execute on real work.

🎯 Learning objectives

# What you will be able to do The real problem it lets you answer
1 Tell apart chatbot, workflow and agent, and say which abilities the word "agent" is actually claiming Why is Claude Code not just a smarter chat box? Because it reads your files, writes files, runs commands, and changes its plan halfway through when the first attempt fails.
2 Install it and give one instruction built from three parts — context, task, output format — on a piece of your own real work "The same tool produced something useful for her and something useless for me." The gap is almost never the model. It is which of the three parts you left out.
3 Locate the two checkpoints inside a single run — the plan it announces before acting, and the permission prompt — and say what each one is protecting you from Everyone says "keep a human in the loop." Where exactly is the loop? If you cannot point at it on your own screen, you do not have one.
4 Judge, for one task you actually do every week, whether to hand it over, split it, or keep it Can someone who cannot code use this seriously? The deciding factor turns out not to be technical skill but knowing which half of a task is yours.

🤖 Pre-class AI workout

Use an AI as your study partner before class. Paste the prompt below into any ordinary chat window — ChatGPT, Gemini, or Claude in the browser. The point is to make the chat window tell you what it cannot do.

I am about to install Claude Code, which is an agent that runs in a terminal on my own computer. Before I do, I want to understand what you, in this chat window, cannot do. Answer these four questions directly, with no preamble. (1) Can you open a file that is sitting on my desktop right now, and if not, what exactly stops you? (2) If I paste the contents of that file into this chat and ask you to fix it, does the file on my desktop change? (3) When a tool is described as an agent rather than a chatbot, which specific abilities are being claimed? (4) Name one task in a university student's week where that difference would change how long the task takes. Do not tell me about your training data or your knowledge cutoff, and do not give me a general list of AI capabilities.

Then ask it this one question:

Now argue the other side. Name two things this chat window does better than an agent that can touch my files.

Bring the answer to question 4 with you. Compare it with the person sitting next to you: if your two tasks turn out to be the same kind of task, you have found what most of the room actually wants this tool for.

A chatbot answers, a workflow repeats, an agent decides

The word "agent" is used loosely enough to be worthless in marketing copy, but it makes a specific claim. Two abilities separate the three, and both of them are visible on your screen within the first five minutes of using Claude Code.

Touches your files? Changes its plan when something fails? What it looks like
Chatbot No — you paste in, you copy out No — one question, one answer A browser tab
Workflow Yes, in a fixed order No — the same steps every time, including the wrong ones A scheduled script, a Zapier automation
Agent Yes, and it decides which files Yes — it reads the result and tries again Claude Code in your terminal

The second column is the one people underestimate. A workflow that fails produces the same failure a thousand times. An agent that fails reads the error message and takes a different route, which is useful when you are right and expensive when you are wrong — because it will also route around your intention.

An agent plans, acts, and checks its own work

Tekton, the team that won the Claude Opus 4.8 Build Day hackathon, reconstructed historical buildings in 3D and had the model verify its own reconstruction: independent verification sub-agents scored the work in isolated contexts, and a self-correction loop kept checking component placement until twenty tests passed, across 339 incremental build stages. See Claude Build Day Hackathon.

Nobody sat there approving 339 stages by hand. The verification was designed into the loop before the building started, which is the whole difference between running an agent and watching one.

Plan, act, check: a chatbot does the first two badly and the third not at all. What you are buying with an agent is the third one, and only if you specify what "checked" means.

Getting it running: four steps, and the place each one breaks

Every step below breaks for somebody, and every break has a recognisable message. Knowing the message in advance is the difference between a two-minute fix and giving up.

Step What you do Where it breaks, and what you will see
1 Check you have a runtime (Node.js) command not found — the computer does not recognise the word yet, which means it is not installed or not on your PATH
2 Install the Claude Code CLI Permission errors on macOS, administrator prompts on Windows, or a corporate or campus network blocking the download
3 Sign in and authorise The browser tab opens and you miss it, or you paste the key into the wrong window. A key is a door key: never paste one into a group chat
4 cd into the folder you want to work in, then start it Nothing breaks visibly here, which is exactly why this is the step that ruins the next ten minutes

If you get stuck, say so out loud rather than quietly falling behind. Everybody in the room hits at least one of these four, and the fix is usually one line.

It only sees the folder you started it in

Claude Code works inside a working directory. Whichever folder you were standing in when you started it is the folder it can read, and files one level up are invisible to it unless you say so.

This produces the single most common beginner failure: you ask it about a document, it tells you it cannot find any such file, and you conclude the tool is broken. It is not broken. You are standing somewhere else.

For students · A quick way to check where you are standing

Ask it, as your very first instruction: "List what you can see in this folder and tell me which folder you are in." If the answer does not contain the file you brought, quit, cd into the right place, and start again. Ten seconds now, ten minutes saved later.

One instruction has three parts: context, task, and output format

Treat the instruction as a handover to a capable new colleague who does not know your work. Three things have to be in it, and beginners leave out the same two.

Context — what this material is and who it is for. "This is a transcript of an interview I did with a bookshop owner for a class assignment."

Task — the verb, and the scope. "Pull out the three claims she makes about why foot traffic dropped, and give one line of her own words as evidence for each."

Output format — the shape you want back. "A bulleted list, no more than two lines per point, in the same language as the transcript."

The vague version fails in a predictable direction

"Help me tidy this up" is not a small version of the instruction above. It is an instruction with two of the three parts missing, and the model fills the gaps with the most statistically ordinary interpretation available: a summary, in its own voice, at whatever length it feels like. You did not ask for that, but you also did not ask for anything else.

This is the pattern the whole course keeps returning to. Anything you leave unspecified gets filled in with a plausible default, and plausible defaults are where product decisions quietly get made for you — the same failure the PRD Stress Test in W11 is built around.

It announces a plan before it acts, and that is your first checkpoint

Before touching anything, Claude Code tells you what it intends to do. Most people skip this text because it looks like preamble. It is not preamble, it is the cheapest review you will ever get: the moment when the difference between what you meant and what it understood is still free to fix.

Read it and ask one question — is this what I meant? If the plan is wrong, stopping now costs one sentence. Stopping after it has rewritten eleven files costs your afternoon.

The permission prompt is the brake, and holding down yes removes it

The second checkpoint is the approval it asks for before reading or writing files and running commands. This is the human in the loop that everybody claims to have. It only exists while you are actually reading it.

Research on human–machine teams calls the useful version of this adaptive autonomy: being able to slide along the scale of how much you let the system do, depending on the step, beats sitting at either extreme permanently. See adaptive autonomy. A first draft, let it run. Anything that overwrites your own work, brake and look.

For students · Where the two checkpoints sit

The plan comes before anything happens and protects you from the wrong task. The permission prompt comes before each action and protects you from the wrong file. They fail differently, which is why you need both — a correct plan can still delete something you wanted.

The person who got the most out of this at Anthropic could not code

Jared Sires worked in sales at Anthropic and had never written a program. Using Claude Code, he turned his own workflow into a product, saved himself two to three hours a day, and ended up moving into a GTM engineering role built around exactly that. See GTM Engineering at Anthropic.

His starting move is the one you are about to make: open the tool, find one task that slows you down, and ask it how it would solve that. Not "learn the tool, then find a use." The other order does not work.

What the research says about the division of labour

Generative AI systems put the human at both ends: someone has to give the instruction at the front, and someone has to check and adjust at the back (Davenport Mittal 2022 How Generative AI Is Changing Creative Work). Studies of prompting practice find that good output comes from iteration rather than one perfect request — image-generation users averaged 7.8 rounds before they were satisfied (prompt engineering).

Read that as permission. If your first result is bad, that is the normal number of attempts remaining, not evidence that you cannot do this.

Hands-on: run one real piece of work through it

The situation. Everyone needs one file to work on for the next ten minutes. If you brought your own, use it: an interview transcript, a report you are drafting, a long email thread, a set of lecture notes. If you did not bring anything, use the shared class file — the full announcement text behind Claude Build Day Hackathon, which is long, written for people already inside the industry, and needs turning into something a first-year student would read.

  1. Put the file into the folder you started Claude Code in, then ask it what it can see
  2. Write one instruction with all three parts: context, task, output format
  3. Read the plan it announces, and stop it if the plan is not what you meant
  4. Approve or refuse each action deliberately, rather than pressing yes on autopilot
  5. When the result arrives, mark one thing it did well and one thing you had to fix yourself

Keep both marks. They are what you bring to the pair review, and the second one is more useful than the first.

⚠️ Common misconceptions

What students assume Why it is wrong What to do instead
"It is ChatGPT with a terminal" A chat window cannot open your file, change it, or run anything. The environment is the product, not the wrapper Watch what it touches on your disk during the first run
"It cannot find my file, so it is broken" It only sees the folder it was started in Ask it which folder it is in, then cd and restart
"A longer prompt is a better prompt" Length is not the variable. A three-line instruction with context, task and format beats a paragraph of adjectives Check which of the three parts is missing before adding words
"Approving everything is faster" It is, until the run that overwrites something you needed. The prompt is the only brake in the system Read the plan once, then approve deliberately
"If the first answer is bad, the tool cannot do it" Practitioners iterate several times as a matter of course Change one part of the instruction and run it again
"I cannot code, so this is not for me" The Anthropic case is a salesperson with no programming background saving two to three hours a day Bring your own slow task, not a programming problem

In short

  • An agent is claiming two abilities a chat window does not have: it touches your files, and it changes its plan when something fails.
  • Almost every bad first result traces back to one of two things — you were standing in the wrong folder, or your instruction was missing context or output format.
  • You have exactly two checkpoints, the announced plan and the permission prompt, and both stop working the moment you stop reading them.
  • The question to leave with is not whether you can operate the tool. It is which half of your weekly work you are willing to hand over.

💬 Discussion and reflection

Pair review

The situation. You and your partner are both on the same student association event team. The publicity lead has dumped a folder on you: a 40-minute recording of last year's post-event review meeting, a messy spreadsheet of last year's ticket sales, and a half-written sponsorship letter. Everything is due on Friday. You have each just run one of these through Claude Code.

  1. Show each other your instruction, and label its three parts out loud — context, task, output format
  2. Point at one place the tool genuinely helped, and one place you had to step in
  3. Decide together which of the three remaining items in that folder you would still not hand over, and say what makes it different

Finish by rewriting your partner's weakest part for them, in one line.

情境：你和夥伴在同一個系學會的活動組。公關組丟了一個資料夾給你們：去年檢討會 40 分鐘的錄音、去年售票的亂七八糟試算表，還有一封寫到一半的贊助信。星期五要交。你們剛剛各自用 Claude Code 跑過其中一份。

  1. 互相看對方下的指令，把三段各是什麼講出來——背景、任務、輸出格式
  2. 各指出一處它真的幫上忙，以及一處你必須自己出手修
  3. 一起決定資料夾裡剩下的三件事，哪一件你們仍然不會交給它，並說出它跟別的差在哪

最後幫對方把最弱的那一段重寫成一句話。

Individual reflection

Write one sentence to keep: "If this were my weekly work, the part I would hand over is __, and the thing stopping me from handing over more is ____ — the interface, the trust, or not knowing what it can do."

✍️ Take-home task

Run one real piece of work through Claude Code before next week. Record one thing it got right, one thing it got wrong, and one line on how you would change the instruction next time. Bring the wrong one — that is the material for Skill Race.
