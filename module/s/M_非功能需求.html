非功能需求

  • 為何 vibe coding 時代反而更該學：AI 很會做出「功能正確」的東西——按鈕按了有反應。但它預設不會主動處理「夠快嗎、夠安全嗎、人多會不會垮、好不好用」這些你沒明講的需求。功能需求是「能做什麼」，非功能需求是「做得多好」——後者正是 demo 與真產品的分水嶺，也是 vibe coding 最常見的隱形地雷。

核心

功能 vs 非功能： - 功能需求：系統做什麼（能搜尋、能下單）。 - 非功能需求（NFR）：系統做得多好——這些 AI 不問就不會做。

最該記住的幾類 NFR（用「-ility」記）： | 類別 | 它在問 | vibe coding 常見地雷 | | --- | --- | --- | | 效能 Performance | 多快？多少人同時用不會慢？ | demo 一個人很快，100 人一起就垮 | | 安全 Security | 資料會不會外洩？能不能被亂搞？ | AI 預設不防 SQL injection、把密鑰寫死在前端 | | 可用性 Usability | 一般人會不會用？無障礙？ | 工程上能跑，但流程反人性 | | 可靠性 Reliability | 會不會當？當了會不會掉資料？ | 沒有錯誤處理，一遇例外整個崩 | | 可擴展性 Scalability | 用戶/資料長十倍還撐得住嗎？ | 架構綁死，要長大得重寫 | | 可維護性 Maintainability | 之後改得動嗎？ | AI 生出一坨沒人看得懂、不敢動的程式 |

NFR 一定要「可量化」：「要很快」沒用，要寫「95% 的請求在 2 秒內回應」「支援 1000 人同時在線」——否則無法驗收（連回 規格書與 Gherkin 行為規格）。

vibe coding 接法：把相關 NFR 明確寫進給 AI 的需求，尤其安全（資料、認證、密鑰）一定要主動提，AI 預設不會幫你想周到。然後針對 NFR 設驗收方式：壓力測試量效能、檢查清單查安全。功能對了只是及格，NFR 才決定能不能真的上線。

💬 互動

  • 一起想一題：一個「會員系統」AI 做出來功能都對，但上線前你最該追問哪 3 個非功能問題？（密碼怎麼存？多人同時註冊會怎樣？個資外洩風險？）

  • 反思：「我驗 AI 的產品，是不是只看『功能對不對』，忘了問『夠快嗎、夠安全嗎、會不會垮』？」

  • 小作業：替你的產品列出每類 NFR 至少一條可量化的需求，標出哪一條若沒做到會讓產品無法上線。
