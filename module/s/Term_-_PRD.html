PRD｜產品需求文件

Product Requirement Document

The document that says what gets built and how you will know it is done — written for the people who build it.

說明「要做什麼、做到什麼程度算完成」的文件，寫給要動手做的人看。

What this term means｜這個詞在說什麼

A PRD answers what counts as finished. Its readers are engineers and designers, so every requirement in it has to be checkable.

A defensible PRD carries: feature descriptions, acceptance criteria, flows and states, permissions, and edge cases. Permissions and states are the section people skip, and they are exactly what the arguments after launch are about.

PRD 回答的是怎麼做才算做完。它的讀者是工程師與設計師，所以每一條需求都要能被驗收。

一份站得住的 PRD 至少要有：功能描述、驗收條件、流程與狀態、權限、邊界情況。權限與流程狀態那一段最常被漏掉，而那正是上線後最容易吵架的地方。

Common misconceptions｜常見誤解

  • Writing the PRD as a vision. The vision belongs in the MRD; a PRD only handles what can be verified.

  • Writing only the happy path. A PRD with no edge cases hands the judgement calls to whoever is coding that day.

  • 把 PRD 寫成願景。願景在 MRD，PRD 只處理可驗收的東西。

  • 只寫快樂路徑。沒有寫邊界情況的 PRD，等於把判斷丟給工程師自己猜。

Related terms｜相關詞

MRD、User Story、Acceptance Criteria、Functional Spec
