Vibe Coding 做小工具

橫跨 2 個 45 分鐘 slot（上＋下，practice）。跨課共用。

🎯 學習目標

每條目標都是「一項能力 → 能解釋一個真實問題」。學這個不是為了學會寫程式，是為了讓沒有工程背景的你，真的做出並發布一個別人能用的小工具。

# 你會的能力 讓你能解釋的真實問題
1 撰寫一份三件套規格（一句話規格／不做清單／驗證點），並 vibe coding 出可跑雛形 為什麼一開頭就叫 AI 寫 code 常常做歪？規格留白的每一處，AI 都會用『看似合理但其實錯』的預設替你填。
2 判斷 AI 產出的失敗模式（幻覺／預設亂填／改 A 壞 B／邊界爆），並用「開乾淨對話讓 AI 審計」修補 為什麼在原對話問「這有沒有問題」它都說沒事，換個全新對話一問就抓出一堆？因為模型對自己的作品評分很差。
3 評斷一個做好的工具值不值得正式導入團隊 「做得出來」之後，主管真正難的判斷是什麼？——用「省下的時間 × 頻率 × 人數 vs 維護成本 × 出錯風險」權衡。AI 不會主動跟你說「這太貴、不該留」，那是人的工作。
  • 上：做出雛形。
  • 下：做完、發布；主管評估「值不值得正式導入」。
  • 小作業：完成並發布工具，寫「AI 幫我做到／我得自己補」反思。

與 AI 互動的工法：Tekton / Yingzao（Build Day 冠軍）

來源 Claude Build Day Hackathon。示範「人怎麼帶 AI」而非「AI 幫你打字」。

  • 先規劃再動工：冠軍第一條建議 "Map the whole project before you build any of it." 先寫好 PRD（見 PRD 撰寫與壓力測試 範本）＋ Notion 50 工單，才讓 AI 開始——用規格控制 AI，不是被 AI 牽著走。
  • 不信任 AI 自評，設外部驗證：PRD 白紙黑字寫「模型對自己的作品評分很差」，所以驗證者跑在全新 context window 獨立評分；自修正迴圈反覆檢查到通過 20 項測試（done.評分標準.json），共 339 個增量構建階段。這是與 AI 互動的核心紀律——把把關機制設計進流程，而非事後人工抽查。
  • 用 AI 選工具、做架構決策（季軍 Custom Universe）：「Use Claude to choose tools, not just to write code」——把「要不要把 Apple RealityKit 加進 pipeline」這種決策也丟給 AI 一起想。
  • 互動練習：學生對自己的小工具，仿照寫一條 one-line 規格 + 一個「不做清單」+ 一個外部驗證檢查點，再開始 vibe coding，比較有無規格控制的產出差異。

💬 討論／分享／反思

  • 成果快展：demo 自己發布的工具，講「最意外 AI 幫你做到的一件事」。
  • 一起想一題：「這個東西值不值得正式導入團隊？」用一個判準回答——維護成本 vs 省下的時間。

  • 反思：「沒有工程背景的我，剛剛真的做出能用的東西了嗎？這改變了我對『誰能做產品』的看法嗎？」

  • 小作業：完成並發布工具，寫「AI 幫我做到／我得自己補」反思。

連結 / 關係

  • 先修鏈：Claude Code 上手（安裝、第一個指令）→ Claude Code 串工作流（設計 skill、接 MCP）→ 這一堂（把規格做成並發布一個能用的小工具）。同一套「描述需求＋驗收＋迭代」心法，逐步放大。
  • 導入決策的下游：變革管理與導入——這一堂尾段「值不值得導入團隊」的判斷，正是那一堂「個人工具→驗證→產品化→分發」微縮生命週期的起點。
  • 每週輪替的分享場：工具箱分享——把發布的工具帶去 demo、互評、歸檔。
  • 背後的不確定性工程：Harness Engineering 與資訊熵——「規格留白 AI 就自作主張」用 entropy 講就是「沒砍掉的不確定性它硬補」。
